# 参数与取舍

全部参数写在 `sources/main.swift` 里，改动后重新编译并 `launchctl kickstart -k gui/$(id -u)/com.kent.dl-wake-fix` 生效，不影响辅助功能授权。

| 参数 | 当前值 | 说明 |
|---|---|---|
| 救屏触发 | 亮屏、显示配置和 USB 事件 | AppKit 后台应用在 Aqua 会话接收通知；事件后才安排检查 |
| 唤醒路径等待 | 3 秒，面板集合变化可延后至亮屏后 10 秒 | 给先后回来的两块屏留出时间；检查时两块都未出现，则再等一个 10 秒的初始化窗口 |
| 重连路径等待 | 10 秒 | 给新接入的 FlipGo 枚举时间，双屏齐全或 USB 断开时取消 |
| 重启后冷却 | 10 秒 | 重启后仍缺屏时，安排一次延后检查 |
| 重试计数重置 | 双屏持续正常 10 秒、熄屏或换接 USB | 短暂的假恢复不足以重置重试计数 |
| 每轮最多重启 | 3 次 | 给长熄屏后的假恢复留出重试机会 |
| 面板识别 | 活动显示器名 + USB `17e9:6000` 在线状态 | 按 `FlipGo-D1`、`FlipGo-D2` 判断 |
| kill 到 open | 按 PID 每 50ms 检查旧进程退出，上限 5 秒 | 实测 0.4～1.4 秒退出；旧进程退出后若已被 DisplayLink 自带助手拉起，就不再 open |
| 布局冻结 | 缺屏那一刻 | 还原以冻结的这份为准，还原期间每轮都先写回，防止被错误位置覆盖 |
| 窗口还原时机 | 恢复后第 2、5、10、20、30 秒 | 每轮幂等（已就位的窗口不重复移动）；后几轮兜住晚出现的 Electron 窗口 |
| 还原后暂停记录 | 35 秒 | 晚于最后一轮还原，避免把还原过程中的中间位置存成新基准 |
| 正常时记录间隔 | 15 秒 | 代价：熄屏前最后 15 秒内挪过的窗口会被还原到挪之前的位置 |

## 原轮询版本的实测耗时

| 版本 | 亮屏到两屏齐 |
|---|---|
| 初版（3 秒轮询 + 连续 4 次 + 固定等 2 秒） | 13～18 秒 |
| 唤醒路径 + 查进程退出 | 9 秒 |
| 轮询改 1 秒 | 6 秒 |
| 冷却 30s → 10s + 恢复后清零（长熄屏假恢复场景） | 从 40 秒降到 8 秒左右 |

剩余开销：3 秒观察窗（安全余量）+ 约 2 秒驱动重建（不可控）。

## 长时间熄屏的特殊情况（2026-10-12 发现）

34 个睡眠周期里只有 1 次需要二次重启，但那次不是随机的：

| 熄屏时长 | 周期数 | 需二次重启 |
|---|---|---|
| 几分钟 ~ 12.9 小时 | 33 | 0 |
| 38.8 小时（周末） | 1 | 1 |

长时间断电后，FlipGo 的 D2 面板彻底放电、主控唤醒更慢，DisplayLink 会先按 1280×800 兜底模式建出来、拿不到正确 EDID 再销毁重来（日志 09:21:23.768 `CDVirtualDisplayDestroy`）。这一抖导致刚恢复就又掉，而当时的 30 秒冷却把重试拦住了 28 秒，体感就是"开机卡了 40 秒"。事件版本同样保留重试窗口，并要求双屏稳定一段时间后再重置计数。

注意：长熄屏样本只有 2 个，这个规律是机制推断而非统计结论。

## 窗口漏挪导致错误位置被固化（2026-10-26 发现）

11:37 亮屏后只还原了 2 轮（第 2、5 秒），当时窗口列表里只有 4 个窗口，Codex 和 Paseo 还没出现，所以没被挪回 D2。20 秒后恢复记录，把它们在 D1 的错误位置存成了新基准；13:24 再亮屏时，还原认为"位置正确"，0 个需要移动。

修改：缺屏时冻结布局，还原期间每轮先写回冻结版本，5 轮还原覆盖到第 30 秒，35 秒后才恢复记录。日志里会记录冻结时和还原后的布局摘要（`froze layout:`、`layout after restore:`），下次出问题可以直接对比。

## macOS 27 与重启互踩（2026-11-02 发现）

升级 macOS 27.2 后两类新现象：

1. **配件连接授权**：重启后系统把 FlipGo 所在的 USB-C 口判为未授权，USB2/USB3 数据通道被拦，只剩供电。DisplayLink 看不到设备，守护进程记录 `dock=false` 不动作（预期行为）。在「系统设置 → 隐私与安全性 → 允许配件连接」改成「始终允许」后不再拦截（日志 `authorizationStatus: 2 [Policy Authorized]`）。
2. **开机时线已插着，USB 不激活**：授权通过后 USB2/USB3 仍不激活，需要插拔一次线。开机后再插线则 1 秒内连通。脚本无法处理：设备不在 USB 总线上，重启 DisplayLink 没有对象可连。

同日发现脚本缺陷：插线时恰好唤醒屏幕，走了唤醒快速路径 3 秒后就重启；DisplayLink 刚插线需要十几秒初始化，这次重启耗时 12 秒，而 `Process.waitUntilExit` 会转主 runloop，1 秒定时器在等待中重入，又触发第二次重启把刚拉起的进程杀掉。修复：

- 加重启锁 `restarting`，定时器和唤醒路径在重启期间都跳过
- 唤醒快速路径只在**熄屏那一刻扩展坞就在线**时生效；新插上的坞交给 DisplayLink 自己建屏，10 秒后仍缺屏由慢速路径兜底

## 重启空等 9 秒（2026-11-03 发现）

亮屏后两块屏 1.5 秒内就绪，窗口却要 10 秒后才归位。原因在"等旧进程退出"的循环：它按进程名查询 DisplayLinkUserAgent 是否还在，而 DisplayLink 自带的重启助手会在旧进程退出后 0.2 秒内把它重新拉起，按名字轮询看不到这个空档，一直等到计数上限（每轮实际约 0.3 秒，3 秒上限变成约 9 秒）。等待期间重启锁挡住了定时器，窗口还原跟着推迟。

修复：杀之前记下旧 PID，用 `kill(pid, 0)` 每 50ms 检查；旧进程退出后如果已有新实例在跑，就不再执行 `open`。修复后实测重启 0.4 秒，两块屏就绪后 2 秒窗口归位。

## 关键实现细节

- **使用 AppKit 事件循环接收通知**：launchd 启动的命令行探针在 2026-10-09 和 2026-11-27 的实测中没有收到亮屏通知。2026-11-27 的 Aqua 会话实测中，用应用包启动并运行 `NSApplication.run()` 后收到了亮屏通知和显示配置变化。
- **USB 匹配不能只给 `idVendor`**：IOKit 的 USB 匹配字典要求同时提供 `idProduct`，只给 vendor 会匹配不到任何设备。匹配 `IOUSBHostDevice` 时同时指定 FlipGo 的 `idVendor == 0x17e9` 与 `idProduct == 0x6000`。
- **`dl-winlayout` 必须用 disclaim 方式 spawn**：否则 TCC 按父进程（`dl-wake-fix`）判定权限，子进程返回 `NOT_TRUSTED`。实现见 `sources/main.swift` 里的 `responsibility_spawnattrs_setdisclaim`。
- **熄屏必然锁屏**：锁屏时辅助功能 API 读到 0 个窗口。因此锁屏期间不记录布局，读到空列表时回退到上一份记录，还原则等解锁后再执行。
